# First-slice migration review — 2026-11-02

Assessment of the local, uncommitted migration based on the accepted alpha
contracts. This is a focused review, not a security audit or a release approval.
No implementation fixes, commits, remote workflow runs, releases or deployments
were performed during the November 2 review. The pre-existing Workspace test edit
remains outside this review. The November 4 follow-up below records the fixes.

## Findings

### F1 — P2: canonical export can exceed the accepted byte limit

Location: `packages/concord/src/runtime.ts`, `openDocument`, lines 614–621.

Protocol verification bounds the incoming transport bytes. A ready open then
canonicalizes them without checking the resulting length. Canonical JSON can be
larger than transport JSON: integral exponent notation is accepted on import but
expanded on export.

Reproduction through freshly built public exports:

1. Read `docs/concord/vectors/owner.document.json` and its owner's seed from
   `owner.expected.json` (`identitySeedHex`). Construct the owner with Armour's
   `identityFromSeed`.
2. Set unsigned container metadata to `{ n: 1000000000000000 }`. Serialize with
   `JSON.stringify`, then replace that numeric token with `1e15`.
3. Open with the register model, standard profile, owner capability, and
   `limits.maxBytes` equal to this transport's byte length.

Observed: the 3,941-byte input protocol-verifies, open publishes ready, and export
is 3,953 bytes. The same handle's `verify()` immediately reports unsupported with
`RESOURCE_LIMIT`. Thus ready state and verification disagree without any mutation.

Required correction: enforce the canonical export bound before publishing ready.
Retain the original bytes for an over-limit inspection handle. Acceptance: this
input returns incompatible/resource-limit inspection, remains byte-exact on export,
and never publishes a projection; normal transport variants within both bounds
still become ready and verify successfully.

### F2 — P2: replay applies the wire budget to expanded internal facts

Location: `packages/concord/src/runtime.ts`, `checkSystem`, lines 183–194;
resource failure classification at lines 325–326 and 349–350.

The `json` helper serializes all system replay output and applies `maxBytes` to
that internal representation. Facts occur in both `entryFacts` and `events`, so
this representation can be larger than the signed document. The contract defines
`maxBytes` as the input/export budget, not a serialized-facts budget. The catch
also labels this resource exhaustion as invalid system history, contrary to the
resource-limit/unsupported distinction.

Reproduction through freshly built public exports:

1. Derive an identity from 32 seed bytes each equal to 7.
2. Use the register model with its `set` decision replaced by a conforming
   decision emitting twenty `{ type: "value.set", version: 1, data: { value: "" } }`
   events in one command. Create and dispatch under default limits.
3. Export and reopen with the same model and identity, a new standard profile,
   and `maxBytes` equal to the canonical export length.

Observed: document size is 23,617 bytes; serialized public system output is
25,728 bytes. Independent protocol verification is valid, but open returns
`reason: "invalid"`, `system: "invalid"`, with a protocol-phase `RESOURCE_LIMIT`.
No projection is exposed, but a supported valid history is incorrectly rejected.

Required correction: keep wire and internal resource accounting distinct; retain
bounded validation of extension output without an undocumented smaller effective
document limit. Resource exhaustion must remain an unsupported evaluation, not a
claim of malformed history. Acceptance: this saved multi-event snapshot opens
ready at its exact wire-byte budget and replays identically; genuine limit failures
produce the documented unsupported/incompatible classification.

### F3 — P2: verification failures erase parseable inspection history

Location: `packages/concord/src/runtime.ts`, `evaluate`, lines 240–256;
`packages/concord/src/protocol/verify.ts`, the failure return from `inspectProtocol`.

Inspection history is populated only from a completely verified snapshot. Any
later hash, linkage or signature failure therefore clears it, although bounded
parsing/schema validation already established public envelopes. The inspection
contract calls for raw public history and reserves an empty history for input that
cannot be parsed/interpreted. This matters specifically when diagnosing tampering.

Reproduction: read `owner.document.json`, replace the child signature with
`"A".repeat(86)` (canonical base64url of 64 zero bytes), encode, and open. The
result correctly reports invalid inspection and `SIGNATURE_INVALID`, and export
preserves the original bytes, but `inspect().history` contains zero records instead
of the two parseable commit envelopes.

Required correction: retain bounded, schema-valid public envelopes separately from
verified history, explicitly as untrusted inspection evidence. Never issue a
`VerifiedHistory` or invoke extensions from that evidence. Acceptance: signature,
hash and linkage failures retain detached public envelopes with their findings;
malformed JSON still exposes no parsed history; projection and mutations remain
unavailable in both cases.

## Delivery position and next checkpoint

Existing tag-based publishers remain active definitions. For example,
`.github/workflows/deploy-armour.yml` builds only Armour and then publishes, without
running the new verification/consumer gates or preparing its Identity dependency
through the graph runner. The main-branch release workflows also retain the old
release machinery. Replacement delivery remains explicitly deferred, but these
workflows must be reconciled before release and before treating main as the new
verified baseline. No release path was executed in this review.

Fix F1–F3 with focused regression checks, review the resulting complete diff,
establish coherent commits, and prove a clean GitHub check before expanding into
drafts or membership. This review found no reason to change the accepted protocol
semantics or add a product decision. It does not establish that the remainder of
the migration is defect-free.

## Follow-up — 2026-11-04

F1–F3 are implemented without changing the wire schema or public API. Protocol
verification bounds both transport and canonical snapshot bytes. Its internal
inspection result retains schema-valid untrusted envelopes independently of the
fully verified snapshot. Runtime replay validates individual entry results and
summaries instead of imposing the document budget on repeated aggregate facts;
resource exhaustion returns unsupported/incompatible inspection in either replay
stage. Entry coverage, signer binding, JSON/depth checks and atomic publication
remain enforced.

Six source regression cases cover the three original reproductions, both replay
resource classifications, invalid extension JSON, immutable inspection evidence,
and exclusion of extension execution on invalid/unsupported protocol input. Five
of those cases failed on the original implementation; the invalid-extension guard
already passed. The installed Node consumer also exercises all three corrected
boundaries against candidate tarballs. Verification results follow once run.
